## D1 — 產品定位

〔事實〕Owner 確認：**只有我自己用、純 Mac、幾乎沒有舊 .xmind 檔、最在意整體 UI 設計與輸入手感**。

因此重寫產品敍述：

> MindFlow 不是「功能對標 XMind 的心智圖 App」，而是**為我一個人打磨的思考畫布**。成功的定義是「我真的會坐下來用它」，不是功能清單長度。

〔關鍵證據〕Owner 自述「還沒真的用起來，因為太難用」—— 30+ 項功能、429 項檢查全過，卻未達可用門檻。這證實了功能數量與實際價值已經脱鉤。

### 明確不做

- XMind `.xmind` 檔案匯入（無舊檔，純技術債）
- iOS / iPad / 同步 / 協作 / 帳號 / AI
- Pitch、新增結構（時間軸/矩陣/組織圖）、Task Tracking、Gantt
- 任何新匯出格式

## D2 — 互動模型：全面重設（鍵盤優先）

〔Owner 決策〕採用 MindNode 式鍵盤優先模型，寧可破壞現有習慣。

### 新規則（唯一權威定義）

| 輸入 | 未編輯時 | 編輯中 |
|---|---|---|
| 左鍵單擊節點 | 選取（**僅選取**） | 提交並選取新節點 |
| 左鍵單擊空白 | 取消選取 | 提交並離開編輯 |
| `Return` | **編輯選中節點**（全選現有文字） | 提交 + 建立兄弟節點並進入編輯 |
| `Tab` | 建立子節點並**直接進入編輯** | 提交 + 建立子節點並進入編輯 |
| 直接打可見字元 | **取代文字並進入編輯** | 正常輸入 |
| `Esc` | 清除選取 | 放棄編輯，還原原文 |
| 方向鍵 | 導覽節點 | 文字光標 |
| 拖曳節點 | 重新掛載（門檻見下） | 禁用 |

### 硬規則

1. **畫布上禁止任何 `.onTapGesture(count: 2)`**。包含畫布、節點、大綱列、分頁列、括線、關聯線。這是不可協商項。
2. **同一個 view 不得同時掛 `.onTapGesture` 與 `DragGesture`**。需改用單一指標狀態機（位移門檻 + 時間門檻）分派。
3. 一個動作只能有一種觸發方式。不提供「還可以這樣也可以那樣」的替代路徑。

### 證據基礎

〔事實〕`MapCanvasView.swift:123` 與 `:128` 同時存在 `.onTapGesture{}` 與 `.onTapGesture(count:2){}` —— v25.8 只從節點移除雙擊，**畫布未移除**，每一次點擊仍在等雙擊判定。

〔事實〕`ContentView.swift:653/658`（大綱列）、`:269`（分頁列）同樣存在這組配對。`MapCanvasView.swift:755` 另一處。

〔事實〕`MapCanvasView.swift:285`（tap）與 `:300`（`reparentGesture` / `DragGesture(minimumDistance:8)`）掛在同一個 node view。SwiftUI 已知此組合造成拖曳起手跳動與點擊遭吞。

〔推論〕Owner 回報的四種痛感（慢、誤操作、進不去編輯、打字流被打斷）可完全由上述三處解釋。

## D3 — 大幅精簡

〔Owner 決策〕「也可以全部重砍」—— 授權砍到核心。被砍的一律保留在 git 歷史，可隨時取回。

### 保留（核心四件）

- 邏輯圖（右展）**一種**版面
- Tab / Return / 直接打字的鍵盤建立流
- 拖曳重掛（門檻重設後）
- 大綱、搜尋、自動保存、Undo
- `.mindmap` JSON 格式與其契約測試（專案最大資產，不動）
- Markdown 匯入匯出、PNG / PDF / SVG 匯出

### 下架（進 git 歷史）

魚骨圖、括號圖、平衡圖、概要括線、關聯線與標籤、簡報模式、圖片附件、範本、批次多選與框選、子樹批次操作、專注/聚焦模式、多分頁、多視窗、OPML / FreeMind 互通、微調位置、星星與色標。

〔判斷〕每一項下架都釋放了畫布上的手勢預算或 body 重算成本。下架不是放棄，是把互動空間還給核心四件。

## D4 — 驗證方式：自動化點擊

〔Owner 決策〕用 macOS Accessibility API 自動驅動真 App，Owner 只看結果。

〔事實〕可行且無需 Xcode：`osascript` + System Events、`andelf/axcli`（Playwright 風格 CLI，以 `CGEventPostToPid` 背景送事件）、`screencapture` 存證。

〔原則〕**回饋迴路優先於產品修復**。在自動化能量測到「點擊到選取廲遲」之前，任何手感修復都無法證實。

## D5 — 執行順序

S0 回饋迴路 → S1 互動重設 → S2 精簡 → S3 效能地基 → S4 樣式系統

S4（樣式系統 / Theme Editor）是 Owner 付費給 XMind 的真正理由，但**必須等 S1–S3 完成**。在一個不順手的 App 上做美化是浪費。

## 可證偵點

| 若出現這個證據 | 則哪個決策錯了 |
|---|---|
| 移除全部 count:2 後，Owner 仍視為「慢」 | D2 不夠，真因在 per-frame layout，S3 需提前 |
| 精簡後 Owner 發現常想用被砍的功能 | D3 砍過頭，從 git 歷史取回，但需重新審查它占的手勢預算 |
| Accessibility 自動化無法穩定命中畫布節點 | D4 不可行，改為在 App 內建測試指令通道（URL scheme / 命令列旗標） |
| Owner 實際坐下來用了但仍不想回來 | D1 錯了，問題不在手感而在心智圖這個形式本身 |

## D6 執行順序修正（2026-08-28，Owner 外出期間由主 agent 決定）

D5 原訂 S0 → S1 互動重設 → S2 精簡 → S3 效能。實際盤點後改為
**S0 → S1' 精準互動/效能修復 → （待 Owner 確認）S2 → S4**。

理由：把 12 個待砰功能 grep 過一遍，每一個的命中數都在 70-100+，代表它們橫向
糴纏整個 7,338 行。先砰會讓 App 在數小時內處於不可用狀態，而 Owner 的核心痛點
正是「無法測試、還沒真的用起來」。先做小而精準、每項都有行號證據的修復，讓 App
今天就能用，再回頭決定精簡幅度。

**D6 帶出的新問題（需 Owner 裁決）**：既然 D3 的保留清單這麼小（單一邏輯圖版面、
Tab/Return、拖曳重掛、大綱、搜尋、自動保存、Undo、.mindmap、Markdown/PNG/PDF/SVG），
而爛掉的是 UI 層（MapCanvasView + ContentView + NodeView = 1,966 行）與 ViewModel
（1,509 行），Model/FileIO/LayoutEngine/匯出器（約 900 行，狀況良好）全部是保留品。
**「重寫 UI 層」可能比「從 UI 層減法拆出 12 個功能、然後反正還是要重寫互動」更省事。**
兩個選項的證據已備齊，等 Owner 回來裁決。在此之前不做不可逆的刪除。

### S1' 人工驗證結果（2026-08-29，Owner 實機確認）

| 項目 | 結果 |
|---|---|
| 選節點 → 打字 → Return | 只新增一顆兄弟節點，游標留在新節點，不再掉進備註 ✓ |
| 編輯中按 Esc | 正常放棄修改並退出編輯 ✓ |

**因此判定**：T-003 harness 回報的「Esc 對編輯欄無可觀察效果」與「Tab 無法遞送」
**是合成事件的環境限制，不是 App 缺陷**。方向鍵與 Return 可正常遞送，而 Tab/Esc
正好是 macOS 會攜截的兩個特殊鍵。baseline 需將它們記在「無法自動驗證」清單，
不得列為產品 FAIL。
