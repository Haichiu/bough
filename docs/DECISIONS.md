## D1 — 產品定位

## D2 — 互動模型：全面重設（鍵盤優先）

〔Owner 決策〕採用 MindNode 式鍵盤優先模型，寧可破壞現有習慣。

### 新規則（唯一權威定義）

| 輸入 | 未編輯時 | 編輯中 |
|---|---|---|
| 左鍵單擊節點 | 選取（**僅選取**） | 提交並選取新節點 |
| 左鍵單擊空白 | 取消選取 | 提交並離開編輯 |
| `Return` | **編輯選中節點**（全選現有文字） | 提交 + 建立兄弟節點並進入編輯 |
| `Tab` | 建立子節點並**直接進入編輯** | 提交 + 建立子節點並進入編輯 |
| 直接打可見字元 | **取代文字並進入編輯** | 正常輸入 |
| `Esc` | 清除選取 | 放棄編輯，還原原文 |
| 方向鍵 | 導覽節點 | 文字光標 |
| 拖曳節點 | 重新掛載（門檻見下） | 禁用 |

### 硬規則

1. **畫布上禁止任何 `.onTapGesture(count: 2)`**。包含畫布、節點、大綱列、分頁列、括線、關聯線。這是不可協商項。
2. **同一個 view 不得同時掛 `.onTapGesture` 與 `DragGesture`**。需改用單一指標狀態機（位移門檻 + 時間門檻）分派。
3. 一個動作只能有一種觸發方式。不提供「還可以這樣也可以那樣」的替代路徑。

### 證據基礎

〔事實〕`MapCanvasView.swift:123` 與 `:128` 同時存在 `.onTapGesture{}` 與 `.onTapGesture(count:2){}` —— v25.8 只從節點移除雙擊，**畫布未移除**，每一次點擊仍在等雙擊判定。

〔事實〕`ContentView.swift:653/658`（大綱列）、`:269`（分頁列）同樣存在這組配對。`MapCanvasView.swift:755` 另一處。

〔事實〕`MapCanvasView.swift:285`（tap）與 `:300`（`reparentGesture` / `DragGesture(minimumDistance:8)`）掛在同一個 node view。SwiftUI 已知此組合造成拖曳起手跳動與點擊遭吞。

〔推論〕Owner 回報的四種痛感（慢、誤操作、進不去編輯、打字流被打斷）可完全由上述三處解釋。

## D3 — 大幅精簡〔已作廢〕

〔判斷〕每一項下架都釋放了畫布上的手勢預算或 body 重算成本。下架不是放棄，是把互動空間還給核心四件。

### 作廢紀錄（2026-08-31）

〔Owner 裁決〕D3 不是待執行計畫，而是**前提已被證據否證的錯誤決策**。

〔事實〕上列 16 組「下架」功能一項都沒有消失：魚骨／括號／平衡版面仍是 `LayoutEngine` cases；概要、關聯線、圖片、範本、簡報、專注／聚焦、批次選取、子樹操作、多分頁／多視窗、OPML／FreeMind、位置微調、星星／色標都有現存 source 與 checks。

〔反證〕Owner 所說的「幾乎無法測試」最後定位成 D8 的四個容器尺寸缺陷；沒有一項由功能數量、手勢預算或 body 功能分支造成。**功能數量與互動品質沒有因果關係，不得再用砍功能換手感。**任何精簡提案都必須指出可量測的實際成本，不能用「功能多所以慢」代替證據。

〔責任〕D3 由主 agent 提出。它把原本「對標 XMind」的目標改寫成「為一人打磨的思考畫布」，偏離 Owner 原意；D9 已重新劃定對標範圍。D3 原文保留只作反面教材，不再提供執行授權。

## D4 — 驗證方式：自動化點擊

〔Owner 決策〕用 macOS Accessibility API 自動驅動真 App，Owner 只看結果。

〔事實〕可行且無需 Xcode：`osascript` + System Events、`andelf/axcli`（Playwright 風格 CLI，以 `CGEventPostToPid` 背景送事件）、`screencapture` 存證。

〔原則〕**回饋迴路優先於產品修復**。在自動化能量測到「點擊到選取廲遲」之前，任何手感修復都無法證實。

## D5 — 執行順序

S0 回饋迴路 → S1 互動重設 → S2 精簡 → S3 效能地基 → S4 樣式系統

S4（樣式系統 / Theme Editor）是 Owner 付費給 XMind 的真正理由，但**必須等 S1–S3 完成**。在一個不順手的 App 上做美化是浪費。

## D8 — 硬規則：容器尺寸由空間決定，不由內容決定

上述四個缺陷是**同一個形狀**：

| # | 位置 | 症狀 |
|---|---|---|
| 1 | `searchOverlay` 未掛 `if vm.showSearch` | 畫布被永久遮蔽 |
| 2 | `HStack` 內 `Divider()` 高度無上限 | 毛玻璃撐滿整個視窗高 |
| 3 | `ScrollView` 上掛 `Capsule()` 背景 | 半透明橫條抹過整個視窗 |
| 4 | ZStack 被超大子項撐大＋GeometryReader 釘 topLeading | 整張圖偏移到右下、底部溢出 93pt |

**規則：把背景、材質、圖形或定位交給一個容器前，先問它在兩個軸向上的尺寸是誰決定的。**
若答案是「內容」而你以為是「空間」（或反之），就是這個 bug。
SwiftUI 裡常見的四個地雷：`Divider`、`ScrollView`、`ZStack`（依最大子項）、
`GeometryReader`（超大內容釘 topLeading 而非置中）。

這條規則無法用 grep 守門（語意層的問題），所以它是 review 時的強制問句，不是 `verify.sh` 的一行。

## D9 — 對標範圍：只對齊核心編輯體驗（2026-08-31，Owner 裁決）

**裁決：MindFlow 對齊 XMind 的核心編輯體驗，不追求 XMind 全功能等價。**

這項決策取代 D1 的「不對標 XMind」產品敘述、D2 中與 XMind command table 衝突的具體鍵位，以及 D3 的功能下架授權。對齊的基準是節點建立、編輯、導覽與直接操作的手感和語義；鍵位以 `/Applications/Xmind.app/Contents/Resources/app.asar` 的 command table 為準，不以記憶或官方失效頁面為準。

### 為何不做全功能追趕

XMind 的 `LIMITED_TRIAL_FEATURE_COMMANDS_TO_FEATURE_NAMES` 付費閘門表顯示，MindFlow 已經擁有其中大部分能力：SVG／Markdown／OPML 匯出、專注模式、簡報、只顯示分支、多工作表、主題自訂、高解析匯出，以及標記、圖片、概要與關聯線。這些既有能力繼續保留，但不構成「XMind 有什麼就再補什麼」的義務。

### 已裁定不做（不是 backlog 或 roadmap）

Owner 已逐項確認下列缺口都不需要：

- Word／Excel／PowerPoint／TextBundle 匯出
- 任務／待辦管理
- LaTeX 方程式
- 密碼加密
- 自動編號
- 錄音
- 浮動主題對齊
- AI

未來不得把這份清單重新包裝成 parity backlog。新增需求以 Owner 的實際工作流為準；改善手感則找可驗證的互動或效能根因，不再以刪除既有功能代替診斷。
